# Renovate GitOps and Vaultwarden Extraction Design

## Goal

Restore Renovate as a GitOps-managed cluster automation and make it detect the
Vaultwarden server image tag in `vaultwarden/values.yaml`. The immediate failure
mode was that Vaultwarden stayed on `docker.io/vaultwarden/server:1.35.8` until
manual intervention, leaving current Bitwarden clients unable to log in.

## Findings

- No Renovate workload exists in the live cluster: no Renovate namespace,
  CronJob, Job, Deployment, Pod, or ArgoCD Application was present.
- The repo contains `renovate.json5`, but no ArgoCD app or manifests deploy
  Renovate.
- `vaultwarden/values.yaml` stores only `image.tag`, not a full Kubernetes image
  reference or a Helm values `image.repository` plus `image.tag` pair.
- Existing custom Renovate managers cover Immich and kube-vip image tags, but
  not Vaultwarden.
- The current Vaultwarden package rule is monthly. That is acceptable for slow
  infrastructure updates, but it delayed a client compatibility fix that needed
  a faster path.

## Recommended Approach

Deploy Renovate through ArgoCD using the official Renovate Helm chart and
repo-local values. Add a custom regex manager for the Vaultwarden server image
tag and change Vaultwarden scheduling so detected updates are proposed without
waiting for the first day of the month.

This keeps Renovate declarative, follows the repo's multi-source ArgoCD pattern,
and keeps credentials out of Git.

## ArgoCD Shape

Add an Application named `renovate` under `argocd/apps/renovate.yaml`.

The Application should use the existing 2-source Helm pattern:

- Source 1: official Renovate Helm chart.
- Source 2: this Git repo with `ref: repo` so Helm can read
  `$repo/renovate/values.yaml`.

Destination namespace should be `renovate`, with `CreateNamespace=true`.
Automated sync should be enabled with `prune` and `selfHeal`.

Renovate should run as a CronJob rather than a long-lived Deployment. Use
`concurrencyPolicy: Forbid` so overlapping runs cannot create duplicate PRs or
compete for branch updates.

## Credential Handling

Renovate needs GitHub write access. Do not commit a plaintext token.

The chart values should reference an existing Kubernetes Secret named
`renovate-token` in the `renovate` namespace. The secret should contain a
`RENOVATE_TOKEN` key. The repo should include bootstrap documentation showing
how to create `renovate/sealed-secret.yaml` with `kubeseal`, but the encrypted
secret cannot be generated by Codex without the plaintext token.

Until that SealedSecret exists, ArgoCD can create the Renovate CronJob but the
CronJob will not run successfully. This is an explicit bootstrap boundary, not a
runtime secret workaround.

## Renovate Configuration

Keep the existing ArgoCD and Kubernetes managers.

Add a custom regex manager for `vaultwarden/values.yaml`:

- Match the current image tag under the `image:` block.
- Use `docker.io/vaultwarden/server` as the dependency name.
- Use the Docker datasource.
- Use Docker versioning.

This makes Renovate understand that `image.tag: "1.37.1"` belongs to the
Vaultwarden server image, even though the chart value does not include the
repository beside the tag.

Change the Vaultwarden package rule to avoid monthly delay. Vaultwarden updates
should be detected on normal Renovate runs, grouped as `vaultwarden`, and left
for review like other PRs.

## Files To Add Or Change

- Add `argocd/apps/renovate.yaml`.
- Add `renovate/values.yaml`.
- Add `renovate/README.md`.
- Update `renovate.json5`.

No plaintext credential files should be added.

## Validation

Local validation:

- Parse changed YAML files.
- Validate `renovate.json5` syntax.
- Confirm the Vaultwarden regex matches `vaultwarden/values.yaml` and extracts
  `1.37.1`.
- Confirm no plaintext token is present in the diff.

Cluster validation after merge and secret bootstrap:

- ArgoCD shows `renovate` as Synced and Healthy.
- Kubernetes shows a `renovate` namespace and Renovate CronJob.
- A manual or scheduled Renovate run logs extraction of
  `docker.io/vaultwarden/server` from `vaultwarden/values.yaml`.

## Out Of Scope

- Creating a GitHub token or GitHub App credential.
- Committing a generated `renovate/sealed-secret.yaml` without the token.
- Auto-merging Renovate PRs.
- Changing update policy for unrelated packages.

## Risks

- The official Renovate chart values may differ from memory; implementation must
  verify chart keys against the rendered chart or chart documentation.
- Without the secret bootstrap, the deployment is intentionally incomplete from a
  runtime perspective.
- Removing the Vaultwarden monthly schedule may increase PR frequency for that
  one package, but keeps compatibility updates visible sooner.
