## Boundary

A dedicated non-admin bot may GET capabilities/inventory/status and POST immediate low-risk actions or immutable proposals. It cannot approve. The HA-side approval worker sends a preview into one configured private Discord DM channel and polls messages using Discord REST (not another gateway/WebSocket). Only a message authored by the exact configured human Discord ID, in that channel, replying to the worker's exact preview message, with content `APPROVE <proposal_id> <sha256>` authorizes one immutable proposal under the lifetime policy above. Reject bots/webhooks, edited or pre-preview messages, wrong replies, wrong hash/sender/channel, expired/replayed approvals. A chat model boolean never authorizes writes. Allowed sender is supplied as YAML configuration, not hardcoded personal metadata in source. Discord token resides in protected HA operator configuration, never returned by HTTP/MCP or stored in proposals. Approval worker may not be activated before configured independently from bot tools. No admin token is retained in Hermes. No HA users/integrations/update/config/shell/code tools.

## Shared pure policy API

`policy.py`: `PolicyError`, `hash_json(value)`, `validate_action(action, inventory) -> {'action': normalized, 'confirmation_required': bool}`, `validate_spec(spec, inventory) -> native_config_without_id`, `make_proposal(kind, payload, inventory, now=None) -> document`, `validate_proposal(doc, inventory, expected_hash=None, now=None) -> document`. Inventory is mapping entity_id -> {'entity_id', 'state', 'attributes', 'registry_fingerprint', 'name', 'area', 'device_name'}. Runtime obtains fresh registry-backed identities. `registry_fingerprint` is lowercase SHA256. Only concrete exact entity IDs, no wildcards/multiple/domain/area targets, templates, scripts, raw YAML, URLs or arbitrary services. Actions shape {'action':'domain.service','target':{'entity_id':'domain.entity'},'data':{...}}; data optional normalized to {}. All identifiers/parameters require exact types and literal values supported by fresh attributes. Deny unavailable/missing states for action targets. Read-only sensor/binary_sensor states may be automation triggers/conditions. Limit actions <=20, triggers<=10, conditions<=10, title<=160. Document ID `house_manager_general_` + lowercase UUID32; 15-minute expiry for action and legacy finite proposals, explicit null for new automation/edit proposals, includes version=3, kind='action'|'automation'|'edit', created_at, expires_at, bindings per referenced entities, payload, sha256 (hash all other fields). expected_hash is mandatory at privileged manager entry (policy validation may default to doc hash for local inspection only).

Automation spec {'title':str,'triggers':[{'type':'time','at':'HH:MM:SS'} | {'type':'state','entity_id':str,'to':str,'for_seconds':int optional}], 'conditions':[{'type':'state','entity_id':str,'state':str} | {'type':'time','after':'HH:MM:SS','before':'HH:MM:SS'}] optional, 'actions':[action...]}. HA timezone Australia/Melbourne read fresh and supplied in capabilities. Build native triggers/conditions/actions, mode single, no initial_state override. New automation is saved and enabled ONLY after human Discord approval. Proposal preview explicitly says daily/state triggers and all actions plus enabling persistent routine. High-consequence appliance actions in automations explicitly highlighted in preview. No edits to existing automations in this release; IDs owned create-only. Existing nightly automation unaffected.

Control families: light turn_on/off brightness/color/temp validated; fan turn_on/off percentage/preset/oscillation/direction (percentage must be an exact integer, not 40.0); media_player power/play/pause/stop/volume/mute/select_source/sound_mode; switch on/off; select.select_option; number.set_value; climate turn_on/off/set_hvac_mode/set_temperature/set_fan_mode/set_swing_mode/set_preset_mode (set_temperature supports one temperature plus optional hvac_mode, not target_temp_low/high). Support actual current devices (Samsung purifiers, Dyson fan/climate, LIFX light, Movingstyle TV, dryer select and wrinkle switch). No raw button resets/restart/factory commands (those are maintenance, not routine control). Device controls must be bounded by advertised attributes/features when relevant.

Classification: climate activation/mode/temperature/preset changes require approval except turn_off and explicit hvac_mode off; dryer/washer/oven/cook/heater/water-heater or similar appliance names/device metadata on select/switch/number/fan require approval for non-stop/non-off changes. Fan Dyson ventilation/auto allowed directly; requested heat/heating/warm presets require approval even when trusted metadata is innocuous (including fan.turn_on preset_mode). Heating requires approval regardless of fan/climate presentation. Unknown switches/selects/numbers require approval rather than blocking. Known purifier accessory light/night/focus/continuous-monitoring options may be direct. Stop/pause/off permitted without approval. Metadata cannot be supplied by model: server inventory derives it.
